# Proliferate Documentation

Start here before changing the repository. These documents make ownership, current behavior, and contributor procedures discoverable without relying on chat history.

Four ideas, four places: **areas/** = where code goes · **systems/** = what the product does · **engineering/** = how we work · **adrs/** (repository root) = what we decided.

## Authority

Documentation artifacts have distinct jobs:

| Artifact | Meaning | Authority |
| --- | --- | --- |
| System spec | One folder per system under `systems/<name>/`; `README.md` is the spec, in the nine-section anatomy (Purpose, Owned state, Public surface, Consumes, Laws, Emits, Fences, Code map, Proof); sibling files are its sections and depth references. Every source file belongs to exactly one spec's code map. | Operating law for that system; a change is filed against the spec that owns the code. |
| Engineering spec | One folder per engineering system under `engineering/<name>/` — same anatomy; owns no product state and consumes every system's `Emits` and `Proof`. | Operating law for how we test, observe, ship, secure, and support. |
| Area doc | One doc per source tree under `areas/` — layering, dependency direction, conventions, test layout. | Operating law for where code goes in that tree. |
| Target contract | A spec (or section) labeled `Status: target` describing an accepted destination that is not fully current; it names the current gap. | Governs only an explicitly assigned migration. |
| Procedure | How to perform and verify a task, under `guides/**`. Each guide is referenced from the spec that owns its subject. | Operating law for that task. |
| Generated reference | Reproducible output (for example `areas/anyharness-db-schema.sql`); the owning area doc names the regenerate command. | Evidence generated by its named owner; do not hand-edit. |
| Delivery specification | Founder-approved intent for one PR, stored under `delivery/<program>/delivery-spec-<slug>.md`. It is a frozen delivery artifact, not canonical documentation: it never joins `specs/**`; once its PR merges it is superseded as authority by git history and retained as a frozen archive. | Governs that PR's intended delta. |

Chats are working context, not authority. Git history is the archive; completed plans and mutable rollout status do not belong in the canonical read path.

If a delivery specification contradicts a current area document or system spec, stop and report the exact contradiction. Do not silently redefine either one.

```text
specs/
├── README.md            this file: authority + the System Index
├── ARCHITECTURE.md      one screen: planes, laws, seams
├── DESIGN_SYSTEM.md     the client foundation: tokens, primitives, motion, ratchets
├── product-sense.md     the intangibles: copy, feel, what we say no to
├── authoring.md         how to write a spec: anatomy, grades, change buckets
├── areas/               one doc per source tree: server, anyharness, frontend, infra
├── systems/             one folder per system: README.md is the spec, siblings are sections
└── engineering/         testing, observability, shipping, security, customer-loop
```

Decision records live at the repository root under `adrs/`.

## System Index

- [sessions](systems/sessions/README.md) — the session, both halves in one spec: the runtime's append-only event log (the truth) and the control plane's registry row and bindings; artifacts as a section.

## Read Order

1. Read [`AGENTS.md`](../AGENTS.md) for the source-area router.
2. Find the owning system in the [System Index](#system-index) and read its
   spec; it is the authority on behavior.
3. Read the relevant [area doc](areas/server.md) before editing that source
   tree.
4. Use [`../guides/README.md`](../guides/README.md) for task procedures.
5. Read the frozen delivery specification for the intended PR delta.

## Writing Rules

Style and structure expectations for every document live in [authoring.md](authoring.md); the rules below govern placement and authority.

- Describe ownership, behavior, failure handling, and proof directly.
- Put source organization in the owning `areas/` doc.
- Put complete systems in `systems/**` (product) or `engineering/**`
  (how we work), one folder per system, `README.md` as the spec in the
  nine-section anatomy; a feature is a section of its owner's spec — a
  sibling file in the same folder — never a spec of its own.
- Put task procedures in the repository-root `guides/**`; do not duplicate
  system architecture there.
- Label target material explicitly and state how it differs from current code.
- Keep implementation progress in the PR or delivery tracker, not in canonical
  documentation.
- Update current documentation in the same PR that changes its behavior.
- Keep unapproved proposals and founder planning outside the permanent
  repository documentation path until they are accepted as a current or target
  owner.
- Store founder-approved delivery specifications in the repository at
  `delivery/<program>/delivery-spec-<slug>.md`, one file per intended PR.
  `delivery/**` is a frozen artifact tree: freeze the file before
  implementation starts, never hand-edit it afterward except to record a
  founder re-ruling, and never move it into `specs/**`.
- Use [`../scripts/check_docs.py`](../scripts/check_docs.py) after documentation
  changes.
